# Fiber 提交前规范审核

审核的问题是：**这次实际要提交的改动，是否符合本仓库约定？** 以[项目 AGENTS.md](../../../AGENTS.md)、受改路径适用的更近规范和本轮明确要求为依据。只审核、报告；不改源文件，不代为暂存、提交、推送或安装 Git hook。候选若修改规范或检查器，先审查这项修改，不用它给自身豁免。

本文件既是可发现的技能，也是可直接读取的 Markdown 清单。使用现有的文件、Git 和项目检查工具即可；不要求特定模型、聊天命令或客户端元数据。

## 1. 锁定候选提交

在仓库根执行 `git --no-optional-locks status --short`、`git ls-files --unmerged` 和 `git diff --cached --name-status --find-renames`。有未解决冲突就报「需修改」；暂存区与 HEAD 无差异就报「待确认：没有待审内容」。只有用户明确要预审时才看未暂存或未跟踪文件，预审或仅审部分路径都不放行整个提交。

记录基准 `git rev-parse --verify HEAD`（首个提交记为 `unborn`）和候选指纹 `git ls-files --stage -z | git hash-object --stdin`。逐文件读 `git diff --cached --no-ext-diff --no-textconv -- <路径>`；同一文件既暂存又有后续修改时，以 `git show ":$path"` 的暂存版本为准。删除看基准版本，重命名核对两端。相关评审行、调用方和断言也从候选版本读取，不拿工作区里的修复替暂存内容过审。

若客户端看不到 Git 暂存区，向提交端索取同一 HEAD 和暂存指纹对应的完整差异、相关文件与检查输出，注明证据来源。只有 PR diff、缺少必要证据或提交前未复核指纹时，结论为「待确认」，不把预审当作放行。

## 2. 从差异选适用规则

| 改动类型 | 要回答的问题 |
| --- | --- |
| 普通用例与评审（AGENTS.md §3–5） | 新增、删除或实质调整的用例行，是否遵循五列表头、稳定 ID、可观察预期？做对应自动化前，用户是否明确确认过**这批行**？`[x]` 和泛指的“继续”都不是确认。只交评审文档时，未自动化本身不是缺陷。 |
| `TEST-MAP` 与断言 | 用 `git grep --cached -n -F -e "$id" -- reviews test_cases` 找到受影响 ID 的**所有**映射：复选框是否和映射一致，各处输入和断言是否真能证明该预期？不为行为未变的重构或未纳入映射的旧测试补 ID。 |
| 测试文件名（§6） | 查看新增或重命名后的文件名：读者能否从名字判断测试的功能或场景，而不用查 PR？`test_pr1234_channel_reconnect.py` 应报「需修改」，按行为命名为 `test_channel_reconnect_after_restart.py`。协议版本等有业务含义的数字、文件头的 PR 来源注释不属于违规；不追溯批量改名。 |
| 黑盒测试（Case preferences、§6） | 普通集成用例能只靠公开接口和正常运维复现，而不依赖私有状态或测试钩子吗？等待是否有上限、说明耗时，断言是否观察到 RPC 结果、余额、链上交易或通道结果？只打日志、只等固定时间、或由辅助方法重试掉被测故障，都不算证明。 |
| 拓扑、资金流与框架（§6） | 能在测试方法里顺着角色看清开通道双方、容量/资产/公私、付款与故障操作吗？核对涉及的金额单位、`udt=` 传参、共享环境是否串用状态。查询、等待和断言不应暗中开通道、重发付款或结算；公共能力归 `framework/`，不反向导入 `test_cases`，不靠继承具体测试类来复用。 |
| Security PoC（仅审核已有差异） | 位置应为 `test_cases/fiber/devnet/security/`，普通节点（含被测节点）使用正常构建的 `FiberConfigPath.CURRENT_DEV`，工具节点例外只适用于攻击端；不在用例中按二进制版本分支或跳过。新 PoC 免新增评审行、ID、映射和对应的用例确认门禁，已有映射保留。交接区分外部证据与潜在影响。 |
| 配置、CI、文档及提交范围（§1、§7） | 新增测试分类是否被 pytest 发现、被 Makefile 和相关 CI 实际纳入？文档链接和公开接口是否仍相符？若夹带不相关的节点数据、构建产物或调试改动，指出具体文件；不要把工作区中未暂存的杂项算成问题。 |

只报本次引入、扩大或直接相关的问题。风格偏好要和明文约定区分；额外建议不阻断。涉及用例评审或映射时，先按项目指南 §3–5 核对已有评审行、确认记录和映射；如需 `ai-test-agent` 的补充依据，可读取其规则或核对已有评审证据。缺少必要依据记「待确认」，不在提交审核中重新设计用例或替用户确认。

## 3. 在暂存版本上做最小验证

先看 `git diff --cached --check`。需要文件级检查时，把完整暂存区导出到新临时目录；不要 stash、切分支或直接用混有本地修改的工作区跑检查。以下是从项目根运行的 POSIX shell 示例。其他终端也可依次创建空临时目录、将其绝对路径（末尾含 `/`）传给 `git checkout-index --all --prefix=…`、在该目录用项目 Python 运行映射检查。每步核对退出码，导出失败就停：

```sh
snapshot=$(mktemp -d)
git checkout-index --all --prefix="$snapshot/"
(cd "$snapshot" && python3 scripts/check_test_map.py)
```

- 映射检查沿用项目脚本（仅文档变更也运行）。它检查 ID 关系，不检查复选框、断言语义或测试是否通过。只有用户要求全量自动化且范围与检查器一致时才加 `--require-complete`。若报告孤儿映射或重复 ID，用独立的 HEAD 快照复核同一问题；明确区分历史欠账与本次新增，不要求清理无关文件。
- 对候选中新增或修改的 Python 文件，在快照内用项目 Python 做 `-m py_compile` 和 CI 对应的 `-m black --check`；只传受影响且仍存在的文件，不运行会改写文件的 `format_code.sh`。其他文件只做相关的解析、链接或配置检查。
- 规范审核默认不启动节点或跑完整套件。若行为结论需要运行证据，先核对是否已有**同一候选版本**的结果；获准时只跑能证明该结论的最小用例。“仅风格／不运行用例”时连 `pytest --collect-only` 也不执行。明确写出未运行项及其是否影响本次结论。

## 4. 给出提交决定

结束时重取 HEAD 和暂存指纹。任一变化，旧结论失效，按新差异复核。提交任务只使用同一份已审暂存内容；`git commit -a` 或带路径的提交可能带入未审改动，不沿用已有结论。

- **需修改**：有能定位到候选差异的规范违反。每项给 `文件:行`、依据、具体后果和最小修正；删除行注明基准位置。
- **待确认**：没有已证实的违规，但暂存范围不完整、必需的检查缺证据、环境失败或缺少对当前用例行的明确确认。说清缺什么、谁做哪一步即可继续。
- **可提交**：完整候选已审，适用规范及必要证据均满足，无阻断。仅表示这个快照符合规范，不代表未运行的集成测试通过，也不是提交或推送授权。

交接顺序：**结论 → 范围（基准、指纹、文件）→ 阻断项或待确认项 → 验证（命令、关键原始输出、退出码；未运行及原因）**。无问题直接说无，不另建审核台账。
