# Fiber PR 评审规则

审核对象是 pull request 相对基线分支的 diff，不是本地暂存区。只应用与本次 diff 相匹配的规则。只评审，不改测试、不提交、不推送、不合并。

1. 普通用例与评审：新增、删除或实质调整的用例行，是否遵循五列表头、稳定 ID、可观察预期？做对应自动化前，用户是否明确确认过这批行？`[x]` 和泛指的“继续”都不是确认。只交评审文档时，未自动化本身不是缺陷。
2. TEST-MAP 与断言：在 PR 版本中找出受影响 ID 的所有映射。复选框是否和映射一致，各处输入和断言是否真能证明该预期？不为行为未变的重构或未纳入映射的旧测试补 ID。
3. 测试文件名：新增或重命名后的文件名能否让读者判断测试的功能或场景，而不用查 PR？`test_pr1234_channel_reconnect.py` 应报「需修改」，按行为命名为 `test_channel_reconnect_after_restart.py`。协议版本等有业务含义的数字、文件头的 PR 来源注释不属于违规；不追溯批量改名。
4. 回归代码与运行产物：提交的是可长期重复运行的用例，还是一次验证的输出？一次性用例或混入的运行日志、终端记录、生成报告均判「需修改」，指出应移出本次提交的路径。源码中的日志调用、固定测试输入与预期本身不是运行产物。
5. 环境变量前置条件：从用例追到实际使用的 fixture、辅助方法。不额外设置环境变量时，默认 pytest 路径是否仍执行完整断言？必填变量，或缺变量时 skip、提前返回、绕过核心断言，判「需修改」。有可运行默认值且仍验证同一行为的可选覆盖不阻断。
6. 黑盒测试：普通集成用例能只靠公开接口和正常运维复现，而不依赖私有状态或测试钩子吗？等待是否有上限、说明耗时，断言是否观察到 RPC 结果、余额、链上交易或通道结果？只打日志、只等固定时间、或由辅助方法重试掉被测故障，都不算证明。
7. 旧用例与 CI 环境复用：先找同功能旧用例。相同操作和判断依据能否直接补输入或断言？不同场景能否保留独立方法、共用已有测试类？若多条用例重复启动同配置节点，指出可复用的旧类或拓扑，优先采用 SharedFiberTest。核对合并后的原断言、映射和单跑/换序独立性；确需隔离时保留 FiberTest，不只凭基类判违规。
8. 拓扑、资金流与框架：能在测试方法里顺着角色看清开通道双方、容量/资产/公私、付款与故障操作吗？核对涉及的金额单位、`udt=` 传参、共享环境是否串用状态。查询、等待和断言不应暗中开通道、重发付款或结算；公共能力归 framework/，不反向导入 test_cases，不靠继承具体测试类来复用。
9. Security PoC（仅审核已有差异）：位置应为 test_cases/fiber/devnet/security/。普通节点（含被测节点）使用正常构建的 FiberConfigPath.CURRENT_DEV，工具节点例外只适用于攻击端。不在用例中按二进制版本分支或跳过。新 PoC 免新增评审行、ID、映射和对应的用例确认门禁，已有映射保留。交接区分外部证据与潜在影响。
10. 套件组织与入口：同类测试优先按功能归目录，直接用 pytest 或已有 Makefile/CI 入口运行。为某一组测试新增或依赖专用集群启动、用例编排脚本，判「需修改」。新增目录仍核对 pytest 发现与 CI 纳入，不要求搬迁无关旧文件。
